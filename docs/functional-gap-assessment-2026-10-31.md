# 医疗后台功能差距评估（不含订单和外部支付）

## 结论与边界

当前是有多个业务页面、基础录入和查询的医疗管理原型，还不是业务闭环完整的院内系统。主要差距是业务状态、记录关联、人员权限和可追溯性，不是页面数量；无需全部推翻，也不能据此给出可信的“完成百分比”或工期。

本报告只读分析本仓库。已有代表有源码实现，不代表生产验收；“未见”仅指仓库；备份等外部部署能力保持未知。未实现以下新增业务，也没有执行攻击验证。

即使不做支付，目标业务仍需贯通：
**患者建档 → 排班/号源 → 预约 → 到诊/取消/爽约 → 独立就诊 → 诊断/处方 → 发药或检查结果 → 归档与追溯。**

Java 路径以下相对 src/main/java/com/hospital；Mapper 相对 src/main/resources/mapper。

## 已有、未闭环和缺失

| 领域 | 源码事实 | 主要差距 |
|---|---|---|
| 患者档案 | entity/Patient.java、PatientServiceImpl.addPatient：基本资料/账号关联，插入前查重证件 | 稳定患者编号、出生日期/联系方式、按实际需要管理过敏等信息、重复档案处理；查询后插入不能替代并发唯一约束 |
| 患者/医生页面 | login&regist.ftl 按角色跳转，menu.ftl 分菜单；患者部分查询以session找本人，医生就医列表以session找Doctor | 页面分开不等于后端权限隔离；需要功能授权及患者数据范围 |
| 医生/科室 | Doctor实体与Controller提供资料维护，科室为字符串 | 科室字典、人员启停用、停诊及历史关联保留 |
| 排班/号源 | 实体及建表脚本未见排班、时段、容量模型 | 日期/时段/限额、停诊与冲突、并发号源约束 |
| 预约 | Appointment及服务主要为CRUD，患者/医生/日期字段 | 重复预约约束、生命周期状态、变更记录 |

| 独立就诊 | Seek有患者、描述、疾病、药品和科目串 | 缺明确预约关联、接诊医生、就诊时间及状态；需以就诊ID贯穿后续操作 |

| 处方 | PatientServiceImpl.seek解析“药品ID@数量”、扣库存、存字符串 | 处方头/明细、数量单位及必要说明、开立/撤销状态；开方不应自动等于发药 |
| 发药/退药 | 未见独立流程，开药直接扣总量 | 操作人员、实际明细与时间、部分发药、未发取消、退药回库流水 |
| 库存/批次/效期 | Drugs只有总数量等基础字段，SQL直接减number | 入库/发药/退药/盘点流水、预警；真实药房另需批号、效期和失效批次控制，不必先引入采购订单 |

| 权限/账号 | Login有role，菜单隐藏；LoginInterceptor只验session非空 | 后端角色与资源授权、受控管理员创建、账号停用 |
| 审计/历史 | 多个Mapper直接DELETE，未见专用审计模型 | 谁何时查看/修改/作废/导出、版本记录、业务作废归档与基础资料删除区分 |

## 优先于新增页面的四处问题

1. **同一患者多次就诊可能互相覆盖。** SeekMapper.xml 的 updateDrugs 用 patientid 而非当前Seek ID作为更新条件；getSeekByPatientId仅取最后一条。同一患者多条Seek时开药会影响全部匹配历史行。应先引入贯穿操作的当前就诊ID，使处方只绑定当前就诊。
2. **预约不是原子业务。** PatientController.appointment先插入、再查询最近ID、再回写患者；AppointmentMapper用max(id)。并发可能错关联，部分失败可能留下半笔数据。应使用生成键、统一事务和重复提交策略，再加入号源状态。
3. **库存约束不足。** PatientServiceImpl.seek仅检查现存量是否<=0，未比较申请数量；不足后仍有后续写入，SQL无条件扣减，未见事务。先做数量验证、条件扣减和失败回滚，再分开开方与发药。
4. **账号/权限边界须先封住。** LoginServiceImpl.regist对新用户名且空证件号设置role=1，WebConfig又放行/regest；LoginInterceptor对登录角色统一放行。应把管理员创建限制为受控入口，并在后端检查角色和患者范围。仅静态发现，未进行攻击验证。

## 建议的演进顺序

### A：可信底座
受控账号、后端授权、独立就诊ID、关键写入一致性、审计历史、备份恢复。
验收：同一患者两次就诊互不覆盖；患者不能访问他人数据；库存不足不留下部分扣减。

### B：一个完整门诊闭环
人员/科室启停用、排班号源、预约取消报到爽约、接诊病历诊断处方归档；提供药品时加入发药退药和库存流水。
验收：最后一个号源并发不超额；取消释放容量；同一处方重复操作不能重复发药；操作人员与状态可追溯。

### C：按实际机构业务扩展
有检查检验就补执行与结果；有药房就补批次效期盘点；有住院就补床位和入转出，再明确护理范围；有运营需求再补报表。

建议先定位为可靠的小型门诊/院内基础管理后台，再决定是否扩成住院系统。订单、外部支付可完全不做，但记录关联、库存流转、权限和追溯仍然需要。

## 后续授权实施增补（本次本地分支，非生产上线）

以上表格保留最初“不含订单/外部支付”的评估基线。用户随后明确增加的模拟财务能力已在 `finance/FinanceService.java`、`finance/api/FinanceController.java` 及 `db/finance/` 实施：

- 管理员确认模拟充值后入余额及现金账；患者余额支付只记余额流水，不重复算现金收入。
- 管理员按原销售单退款到余额；不提现，不等同实际退药回库。药品采购记录现金支出和库存入库。
- 独立系统支付密码的加盐哈希、仅四位尾号的模拟卡；不接触真实支付机构或真实银行卡。
- 按预约唯一登记完成接诊；医生日/周/月次数与原成交比例提成，退款按快照冲回。
- 订单时固定演示含税税率快照；新初始化默认3%，10元仍扣10元，拆分9.71未税金额与0.29税额。历史单不套新税率。
- 本人/管理员只读模拟购买凭证及PDF，无税务认证含义、不展示佣金；采购/充值/购药/退款报表来自实际隔离账本。
- 新财务接口有角色、归属、CSRF、幂等、并发和事务回滚测试；旧未迁移临床接口的权限与状态闭环仍需单独治理，不能因财务接口安全而推定整站安全。

这些变更**不代表完成真实医院上线条件**：原始病历/处方仍未完全以独立就诊实体贯通；排班号源、检查结果、药品批次效期、发退药、完整审计、备份恢复以及真实MySQL并发/故障恢复验收仍属缺口。H2测试和演示截图不替代临床业务验收。
